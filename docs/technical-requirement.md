# Техническое задание

_**Общие требования**_. Данное техническое задание формулирует следующие требования к вашему ПО:
1. Модуль, реализующий стек, должен быть выполнен как _статическая библиотека_. Это требование выполняется автоматически
([CMakeLists.txt](../CMakeLists.txt)) - весь код из `cstack.c` попадет в библиотеку.
2. Библиотека должна _собираться_, т.е. в ней не должно быть ошибок компиляции и линковки (за исключением ситуации отсутствия на машине
сборки стандартной библиотеки C).
3. Библиотека _не должна иметь зависимостей_ иных, чем стандартная библиотека C.
Не сомневаюсь, что при должном упорстве можно найти готовые реализации стека на С, удовлетворяющие нашим требованиям.
Это не наш случай :smiling_face_with_tear:.
4. Функции библиотеки должны удовлетворять требованиям, описанным ниже.
5. Библиотека должна корректно _освобождать ресурсы памяти_ при должном использовании.
6. Библиотека должна быть _отказоустойчива_ (в разумных пределах) _к входным данным_ функций, т.е. должны быть введены разумные проверки на нулевой указатель, нулевой размер и т.д. Понятно, что проверить валидность переданного указателя (например, что он не указывает в начало адресного пространства) невозможно или очень трудно, но полноценная проверка и не является ответственностью библиотеки.
7. В ходе нормального выполнения и использования кода библиотеки не должны возникать ошибки сегментации, переполнения стека, обращения к
памяти и др.
8. Библиотека не гарантирует: освобождение ресурсов памяти при некорректном использовании функций библиотеки; отсутствие недекларированного
поведения в случае передачи невалидного указателя (за исключением нулевого указателя).
9. Код в файле `cstack.c` должен соответствовать стилю форматирования, определенному в файле
[.clang-format](../.clang-format).
Соответствие проверяется командой `clang-format --dry-run -Werror cstack.c`.
10. Все изменения необходимо вносить только в файл `cstack.c` (допускаются добавление `#include` стандартных заголовков C
и приватные объявления непосредственно в этом файле). Остальные файлы проекта (`cstack.h`, `test.cpp`, `CMakeLists.txt`, документация)
изменять не нужно: CI и код-ревью проверяют только `cstack.c`.

Валидация этих требований будет осуществляться в процессе код-ревью, сборки, статического анализа, юнит-тестирования и проверки стиля кода. Обратите внимание, что последние два
валидатора могут быть выполнены вами в целях экономии времени (в том числе и вашего). Но это лишь предложение по оптимизации процесса
проверки, а не требование. Обратите внимание, что юнит-тесты могут быть модифицированы в случае выявления недостаточности
проверок/несоответствия приведенным выше требованиям. Требования - первичны, а тесты всего лишь их выражают.

_**Особенности нашей реализации стека**_.
1. Библиотека может одновременно обслуживать несколько стеков.
2. Количество одновременно обслуживаемых стеков не должно быть меньше 10. При этом 10 — не жесткий предел:
`stack_get_all` должна успешно работать и при 10 существующих стеках, т.е. для создаваемого стека должен найтись
свободный слот (за счет динамического расширения внутренней таблицы либо увеличенного фиксированного размера таблицы).
3. Данные, хранимые в стеке, нетипизированы.
4. Библиотека не потокобезопасна: одновременные вызовы ее функций из разных потоков не поддерживаются.
5. Хэндлеры не обязаны быть уникальными на все время работы процесса: после `stack_free` освободженное значение
хэндлера может быть повторно выдано новому стеку. Уникальность гарантируется только среди стеков, существующих
в данный момент.
6. Освобождение памяти стека (`stack_free`, `stack_free_all`) должно выполняться итеративно: глубина рекурсии в
реализации не должна зависеть от количества элементов в стеке, чтобы при глубоком стеке не возникало переполнения
стека вызовов.

**_Требования к функциям библиотеки_**.
Одним из аргументов большинства функций библиотеки является _хэндлер_ стека с типом `hstack_t`. Этот тип является псевдонимом типа `int`
и к реализации стека в памяти отношения не имеет. Скорее это абстрактный идентификатор, который нужен, чтобы отличить один стек от другого.
Отмечу, что в C использование _хэндлера_, (_дескриптора_), является стандартной практикой. Примеры:
[hInstance](https://learn.microsoft.com/ru-ru/windows/win32/learnwin32/winmain--the-application-entry-point) в `WinAPI`, возвращаемое
значение функции [open](https://man7.org/linux/man-pages/man2/open.2.html) в `POSIX`. Объявление этого типа находится в заголовочном файле
[cstack.h](../cstack.h).

| Функция | Описание | Параметры | Возвращаемое значение | Особые требования |
|---|---|---|---|---|
| `hstack_t stack_new(void)` | Создать новый стек. | — | `-1` в случае ошибки выполнения, хэндлер нового стека с неотрицательным значением в случае успеха. | — |
| `void stack_free(const hstack_t stack)` | Удалить стек, если соответствующий хэндлеру стек существует. | `stack` - хэндлер стека. | — | — |
| `void stack_free_all(void)` | Удалить все существующие стеки, если хотя бы один из них существует. После вызова функции ни одного стека существовать не должно, и все ранее выделенные библиотекой ресурсы должны быть освобождены. | — | — | Вызов функции в состоянии, когда ни одного стека не существует, не должен приводить к ошибкам и изменениям состояния библиотеки. |
| `int stack_valid_handler(const hstack_t stack)` | Проверить хэндлер. | `stack` - хэндлер стека. | 1 - соответствующий хэндлеру стек существует, 0 - нет. | — |
| `unsigned int stack_size(const hstack_t stack)` | Получить количество элементов в стеке, если соответствующий хэндлеру стек существует. | `stack` - хэндлер стека. | Количество элементов в стеке, если соответствующий хэндлеру стек существует, или 0 в противном случае. | — |
| `void stack_push(const hstack_t stack, const void* data_in, const unsigned int size)` | Добавить элемент данных из буфера в стек, если соответствующий хэндлеру стек существует. | `stack` - хэндлер стека; `data_in` - указатель на буфер с данными; `size` - размер буфера с данными. | — | Если стек не существует, `data_in` - нулевой указатель или `size` равен нулю, функция ничего не делает. При неудачном выделении памяти элемент не добавляется и состояние стека не изменяется (ошибка не сообщается — тип возвращаемого значения `void`). |
| `unsigned int stack_pop(const hstack_t stack, void* data_out, const unsigned int size)` | Извлечь элемент из стека и записать данные этого элемента в буфер, если соответствующий хэндлеру стек существует и размер выходного буфера достаточен для копирования в него элемента стека. | `stack` - хэндлер стека; `data_out` - указатель на буфер для записи данных; `size` - размер буфера. | Размер записанных данных в байтах, если соответствующий хэндлеру стек существует и размер выходного буфера достаточен для копирования в него элемента стека, или 0 в противном случае. | При неудачном извлечении (стек не существует, стек пуст, `data_out` - нулевой указатель, `size` равен нулю или выходной буфер меньше элемента) элемент не извлекается: состояние стека не изменяется. |
| `unsigned stack_top_size(const hstack_t stack)` | Получить размер верхнего элемента стека в байтах, если соответствующий хэндлеру стек существует и не является пустым. Функция, в первую очередь, нужна для определения размера выходного буфера, необходимого для корректного вызова `stack_pop`. | `stack` - хэндлер стека. | Размер верхнего элемента стека в байтах, если соответствующий хэндлеру стек существует и не является пустым, или 0 в противном случае. | — |
| `hstack_t stack_get_all(void)` | Создать новый стек, заполнить его хэндлерами всех остальных существующих стеков и вернуть хэндлер этого стека. Хэндлер самого создаваемого стека в стек включать не нужно. Каждый хэндлер записывается в стек как один элемент размера `sizeof(hstack_t)`. Порядок элементов в возвращаемом стеке не гарантируется. Если в момент вызова функции не существует ни одного стека, возвращаемый стек будет пустым. | — | Хэндлер нового стека с неотрицательным значением в случае успеха, `-1` в случае ошибки выполнения (в том числе при неудачном выделении памяти). В случае ошибки функция не должна изменять набор существующих стеков. | — |

**_Подсказки по реализации_**. Прежде чем давать задание вам, я самостоятельно реализовал стек, чтобы было проще декомпозировать задачу и
подумать, в каких местах стоит дать подсказки. Эта часть необязательна к прочтению, ограничений на реализацию я не ставлю (кроме приведенных
в требованиях).

На мой взгляд, две главные проблемы, которые вам предстоит решить - как хранить сами данные в стеке и как устанавливать соответствие между
хэндлером и стеком.

Первая проблема решалась бы тривиально, если бы мы реализовывали стек, хранящий типизированные данные.
Тогда мы бы на этапе компиляции знали размер одного элемента стека.
Например, если бы мы хранили `int`, размер элемента стека в простой реализации был бы равен `sizeof(int)`.
В этом случае можно было бы вовсе обойтись без динамической памяти.
Для случая неизвестного на этапе компиляции размера я выбрал вот такое решение:
```c
struct node
{
    const struct node* prev;
    unsigned int size;
    char data[];
};

typedef struct node* stack_t;
```
Такой подход напоминает другую структуру данных [односвязный список](https://prog-cpp.ru/data-ols/).
Из общего у них наличие указателя на предыдущий элемент.
При добавлении нового элемента в стек удобно в рантайме посчитать количество данных элемента стека
(размер указателя на предыдущий элемент `prev` + размер поля `size` + размер самих данных), аллоцировать
эти данные и заполнить их.
Это не единственно верный вариант, возможны альтернативы.

Вторую проблему я решил следующим образом: завел глобальный динамический массив указателей на верхушки стека так,
чтобы дескриптор стека являлся одновременно и индексом в этом массиве.
Добавил несколько оптимизаций, но общая идея такая.
```c
struct stack_entry
{
    int reserved;
    stack_t stack;
};

typedef struct stack_entry stack_entry_t;

struct stack_entries_table
{
    unsigned int size;
    stack_entry_t* entries;
};

struct stack_entries_table g_table = {0u, NULL};
```

    **Fork pull request workflows** (запуск workflow'ов из пулл-реквестов внешних форков, требование их
    одобрения и т.д.) — для выполнения домашней работы достаточно значений по умолчанию.

    поэтому первый запуск появится в списке, как только вы создадите пулл-реквест.

    при открытии пулл-реквеста и при каждом обновлении ветки; он выполняет сборку проекта,
    статический анализ кода (`cppcheck` и `clang-tidy`) и запуск тестов.
    **Пока пайплайн не проходит, ревью не начнется.**
    Если вы не понимаете, почему не проходит пайплайн, обращайтесь к преподавателю.
    Подробнее о работе пайплайна и статических анализаторов — в разделе
    [«Работа с GitHub Actions и статическим анализом»](./ci.md).
